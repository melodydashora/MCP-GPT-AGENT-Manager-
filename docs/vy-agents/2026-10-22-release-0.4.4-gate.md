# VY 0.4.4 release gate (full version)

Written 2026-10-22 by a cloud Claude Code workflow for Melody's VY builders. Inputs: Melody Session Bridge notes (project.vy-canis-majoris, roadmap v13 and earlier), her Google Drive (read-only), and current Google Play documentation. Nothing here was checked against the VY source on the phone. A short version for the phone builders is on the bridge at project.vy-canis-majoris / checklist.release-0.4.4.20261022.

Part 1 is the release plan. Part 2 is an independent critic's corrections and additions, and where the two disagree, Part 2 wins. The bridge checklist already merges both.

## Part 1. Release plan

### Target
VY Canis Majoris 0.4.4 (versionCode 20) is a stabilization release containing fixes F (crash), E (private HOME) and C (Build inventory). It goes to the Play internal track first, then to the closed-testing "Alpha" track, where it supersedes release 19 (0.4.3-browser, code 19, still in review). Production comes after 12 or more testers have been opted in for 14 continuous days and Google approves the production-access application. The Agents-tab context-efficiency work is targeted at 0.4.5 (code 21), shipped to closed testing during that 14-day window rather than packed into 0.4.4. The tester clock is the longest step, so recruitment should start today, before code 20 exists.

### Blockers

#### G0: Off-phone backup of the source tree (including the uncommitted F fix) and the Play upload keystore

**Why it blocks.** Process blocker that must be cleared before any E/C edits. The phone holds the only copy of the source: no Git, the last cloud archive is OneDrive 2026-10-19, before Node and all 0.4.x work. It also holds the only copy of the upload key (PKCS12, cert SHA-256 21:13:0C:96…E9:5E). E and C will be edited directly on that single copy. With Play App Signing a lost upload key can usually be reset through Play Console, but that takes days and needs Google's approval. Lost source cannot be recovered at all.

**Fix.** In /root/projects/vy-canis-majoris: git init. Add a .gitignore covering build outputs, *.jks/*.p12/*.keystore, local.properties, artifacts/, any .env*, and the parked files/ocean-parked. Run a secret scan and commit (tag v0.4.3-baseline, then commit F). Push to a new PRIVATE GitHub repo, or put an encrypted tarball (age or gpg) on Drive/OneDrive. Back up the keystore separately: encrypt it, store the passphrase in a password manager and not next to the file, and keep it off the phone. Copy the 11 GB Termux backup off the phone as well.

**Verify on the phone.** `git -C /root/projects/vy-canis-majoris log -1 --stat` shows the F change. `git ls-remote` on the remote returns the same hash. sha256 of the restored keystore copy matches the original. On another machine, `keytool -list -v` on the restored keystore with its passphrase shows SHA-256 21:13:0C:96…E9:5E.

#### F: Confirmed crash: MainActivity.onDestroy and the Stop button call terminal.setUrlListener(null) outside the null guard

**Why it blocks.** P1 crash in release 19 (0.4.3), the build currently in Play review. It fires on rotation, and on exit before the terminal has started, both of which every tester will hit. The pre-launch report crawler rotates and backs out of screens, so it is also likely to log it as a crash. The fix exists in source and passes compile-check, but has not been built or phone-tested.

**Fix.** Move every terminal.* call in onDestroy, onStop, the Stop handler and onSaveInstanceState inside `if (terminal != null)`. Search MainActivity for any other unguarded terminal field accesses on lifecycle paths. Add a host test or stub that calls onDestroy with terminal == null. Build and ship as code 20 with native debug symbols.

**Verify on the phone.** With Developer options > Don't keep activities ON and OFF: (a) rotate before the terminal starts; (b) launch and press Back immediately; (c) tap Stop with no terminal attached; (d) rotate 10 times with a terminal running; (e) switch apps 5 times. Expected: no 'VY keeps stopping' dialog, and logcat (or the Activity journal) shows no NullPointerException from setUrlListener.

#### E: Confirmed security bug: terminal HOME is the project folder, so CLI sign-in tokens (~/.claude, ~/.codex, ~/.gemini) are written into the project

**Why it blocks.** P1 security issue, confirmed on the phone (`echo $HOME` printed .../workspaces/ocean). Closed testers are real users who will sign in to Claude Code, Codex and Gemini in VY's terminal. Their tokens can then end up in project ZIP exports, model context and the Build inventory, and so leave the device. That would also contradict the current Data safety answers. The fix itself is risky: it could break the CLI logins Melody depends on, so it has to be verified on the phone.

**Fix.** In vyterm.c, set HOME to a private directory outside files/workspaces (for example <filesDir>/home). Point XDG_CONFIG_HOME, XDG_CACHE_HOME, the npm cache and TMPDIR into private storage. Keep the working directory set to the project. On the first launch of 0.4.4, migrate .claude, .claude.json, .codex, .gemini, .config, .npm, .npmrc, .cache and .local out of each workspace into the private HOME. Never delete: if the same item exists in several projects, keep the newest and quarantine the rest privately, and log the move in the Activity journal. Independently, apply one shared denylist (dot-config/CLI folders, credential-like names, .env*, *.key/*.pem/*.p12) in ZIP export, ProjectContext, the Build inventory and Build capture, so the problem is covered twice. Add host tests: HOME is not under workspaces, and export/context/Build exclude the denylist.

**Verify on the phone.** In the ocean terminal: `echo $HOME` shows a private path outside workspaces, `pwd` shows the project, and `ls -la` in the project shows no CLI dot folders after migration. `claude`, `codex` and `gemini` each start already signed in without a fresh login, or with a single re-login that persists across an app restart. Export ocean as a ZIP, run `unzip -l`, and confirm none of .claude, .codex, .gemini, .config or .npmrc are present.

#### C: Confirmed: Build refuses with 'Project exceeds the 500-entry build inventory limit' because node_modules and dot-config folders are counted

**Why it blocks.** Any project that has ever run `npm install` cannot use Build, which is the Agents tab's main feature. Ocean had 964 entries, 919 of them in node_modules, which blocks the React/Node work at the top of Melody's list. Testers following an ordinary npm workflow will hit it immediately. The only workaround is to park folders outside the project by hand.

**Fix.** Have the inventory walker skip dependency, generated and config folders: node_modules, .git, dist/build/.next/out where generated, __pycache__, .venv/venv, .cache, the E denylist folders, and .vy. Honor a basic .gitignore subset. Count only files that could actually be shared. When refusing, name the five largest folders and their entry counts in Details. Keep the existing explicit error when the real shareable count is still too large: no silent truncation. Add a host fixture shaped like ocean (964 entries) that must pass, plus a fixture with more than 500 real source files that must refuse with folder names.

**Verify on the phone.** Move node_modules and .gemini from files/ocean-parked back into ocean (.gemini should migrate to HOME under E), turn Build on with Gemini Argon and Astra, and request a small edit. Expected: no inventory refusal, Details lists the excluded folders, the edit applies, and Undo restores the original files with matching hashes.

#### REPORT: Gate (not a confirmed bug): Report response has never been tested from the phone against the live worker

**Why it blocks.** Google Play's AI-Generated Content policy requires apps that generate content with AI to let users report or flag offensive output without leaving the app. Report response is VY's mechanism for this. It was added in 0.4.1 and only host-tested, and the worker's body cap was later changed from 64 KiB to 1 MiB. If it fails silently, VY has no working report path. It is also a 1-minute test.

**Fix.** No code change unless the test fails. If it fails, fix the client or the worker route, and make sure a failure shows a visible error with a retry instead of a fake success.

**Verify on the phone.** On the 0.4.4 build, tap Report response on (a) a short reply and (b) a long reply near the 60,000-character limit. Confirm in the vy-support worker logs or storage that each /report arrived and that responseChars and sentAtMillis match. Repeat in airplane mode: expect a clear error with the draft or report kept for retry.

#### LISTING: Production gate (policy): the store listing, Data safety and compatibility claims must match what 0.4.4 actually ships

**Why it blocks.** Blocks the production application, not the closed upload. These are all open: whether bundles 16 and 19 include Node is unknown (release 16 installs at 48.8 MB, while libvynode.so alone is 93 MB); pip and React are not shipped; CLI runs are owner-reported and not documented reproductions; Data safety says 'collected, not shared' while prompts and project files go to the AI provider the user picks, and Report response sends reply text to the worker. Misleading claims or an inaccurate Data safety form are grounds for rejection or removal.

**Fix.** Run `unzip -l` on the code-20 AAB to confirm whether base/lib/arm64-v8a/libvynode.so is present, and word the Node claim to match. Remove or avoid any pip or React claim until they ship. Describe CLI support as 'runs Claude Code, Codex and Gemini CLI in the terminal (user-supplied accounts/keys)', and only once the QA rows below pass on 0.4.4, keeping a record of version, path and launch command for each CLI. Re-walk the Data safety form for: user-initiated transfers to the chosen AI provider, Report response content, crash data, and optional MCP/bridge traffic. Re-check the IARC answers on unrestricted internet access and user interaction. Remove test projects from the screenshots.

**Verify on the phone.** Install the code-20 build from Play (internal track) on a clean device and compare Settings > Apps > VY > storage, and whether `node -v` works, against the listing text. Every feature named in the listing works on that install.

### Should fix

- **Agents tab: per-turn context ledger behind the 'Context' button (measure before optimizing).** For every request, record and show what was sent, section by section: system/skills, brief, project memory, Activity journal, each file (path, bytes, hash), number of chat turns, estimated tokens, plus the provider's own input/output/cached token counts from the response. Store this in the Activity journal and give a session total. Nobody currently knows how 'Brief + chosen files + recent chat' is assembled, so this is the evidence needed to identify and remove 'triple work'. It is low risk and read-only. Include it in 0.4.4 only if it has tests by code freeze; otherwise 0.4.5.
- **Agents tab: stable-prefix request layout so provider prompt caching works.** Assemble every request in a fixed order: system and skills, then brief and project memory, then a file snapshot sorted by path with no timestamps, then older chat, then the new message. Static content always precedes changing content, which lets OpenAI automatic prefix caching, Anthropic cache_control breakpoints and Gemini context caching reuse the prefix. Check each provider's current caching rules and minimum sizes, because gpt-6-astra and gemini-4-argon specifics are not in the notes. The ledger above then shows whether cached-token counts actually rise.
- **Agents tab: one shared file snapshot for chat and Build (removes chat→Build double send).** Hash files when they are attached. When Build runs after chat, reuse the files already chosen in the conversation rather than capturing a separate set, and tell the user which files Build will send. Ask the model to return only changed files, or diffs where the strict JSON protocol allows it, so unchanged bodies are not echoed back. Whether chat and Build currently overlap is unconfirmed, so confirm it with the ledger first.
- **Agents tab: rolling summary instead of resending long chat.** Keep the last N turns word for word (N shown in the UI). Fold older turns into a short 'decisions so far' block stored in project memory, show it to the user, and let the user edit it. Never drop content without saying so: show 'Turns 1–14 summarized' in the composer footer.
- **Multi-agent 'triple work': guided Review flow (open requirement from task.astra-ultra-ui-api-key-flow v2).** One action sends the brief and approved files to the selected profiles (for example Claude, Astra and Gemini Argon). Replies are collected side by side, merged into a single change set, and the decision is written to project memory automatically. To save tokens, the first agent gets the full files and later reviewers get the brief plus the proposed change set only. Reviewers ask for extra files on demand through the read tools below.
- **Cross-CLI shared project facts (Claude Code, Codex and Gemini CLI in VY's terminal re-learning the same project).** Keep one canonical AGENTS.md per project, built from docs/ARCHITECTURE.md and project memory. Codex reads AGENTS.md natively. Add a CLAUDE.md that imports it (`@AGENTS.md`). Configure Gemini CLI to load AGENTS.md as a context file; the setting name differs between versions, so check the installed one. Have the Agents tab's brief read the same file. This needs no app release and can be done today.
- **Raise limits with no silent truncation: on-demand list_files and read_file tools (plan v1 phase 4, v13 priority 3).** Replace the 8-file / 64 KiB push with project-scoped list_files and read_file tools the model calls only when it needs a file. Refuse path traversal and symlinks, exclude the E/C denylist and binary files, report truncation explicitly, and give the user on/off and revoke controls. Record the new limits after testing above 500 entries and above 8 files / 64 KiB.
- **Undo must not overwrite edits made later by terminal CLIs (FILE-LOCK).** Before Undo restores a file, compare its current hash with the hash Build wrote. If a terminal agent or Python script changed it since, refuse or ask, and keep both versions. This applies to Undo the same optimistic check Build already does on apply.
- **Automated tests for Build failure paths, the Build/Undo UI, and the device runner abort.** Add host tests for a rejected proposal, a conflicting edit, an oversized file, a credential-like path, and an interrupted apply. Find out why the app-process device runner aborts with code 134 before main(), for example a missing class path or LD_LIBRARY_PATH when started by app_process, so device assertions run again.
- **Finish Python device acceptance.** Run on the phone: Stop on a long loop, HTTPS with urllib, the packaging wheel, and no re-run when the Activity is recreated. Record the results in the bridge release note.
- **pip, owner priority 1 (item D), targeted 0.4.5 or 0.5.** Ship pip for pure-Python wheels only, installed per project. Refuse wheels containing .so files with a clear message. This matches Play's Device and Network Abuse rule: interpreted code is allowed under the interpreter exception, while downloading native executable code is not. Apply the same rule to npm native add-ons.
- **React, owner priority 2.** Port the preview kit (melodydashora/MCP-GPT-AGENT-Manager-, branch ccr-46e71b07-3zobv3, commit a233fcb8) into the VY source with its 48 Java and 38 Chromium assertions as host tests, then test on the device. Separately, test whether a Vite/esbuild production build runs under the bundled Node, since esbuild and rollup publish android-arm64 packages (unverified), so a built dist/ can be previewed offline.
- **Remaining open items.** Complete the storage folder-picker grant end to end and read back Drive export bytes. Test bridge OAuth with an authenticated MCP session once the owner consents. Replace the old Drive tester links (0.1.0 and 0.3.0 dev-signed APKs) with the Play join link.

### Play submission steps

STAGE 0 (today, 2026-10-22; no code needed)
1. Finish G0: back up the source to a private Git remote or an encrypted archive, back up the keystore encrypted and off the phone, and copy the 11 GB Termux backup off the phone.
2. Rotate the full-account Cloudflare token and replace it with a token scoped to the vy-support worker. Rotate the Session Bridge owner key and delete the plaintext 'Session Bridge - PRIVATE connection details.txt' from Drive.
3. Start recruiting testers now. The 14-day clock is the longest step, and it runs on tester opt-ins, not on any particular build. I believe a new release does not reset it, but confirm on the Play Console Dashboard. Aim for 15 to 20 testers so dropouts do not break the 14-day streak.
   - VY is PAID. Google's help says closed and open testers must buy a paid app, while internal-track testers install it free. Decide whether testers pay US$0.99 or get promo codes; whether promo codes cover closed-track installs is unverified.
   - Do NOT switch the app to free to get around this: Play does not let a free app become paid again.
   - Testers must be in one of the 10 countries where the Alpha track is available. Add countries if needed.
   - Add testers to the 'VY closed testers' list (or a Google Group) and share play.google.com/apps/testing/com.melody.vycanismajoris.
   - Tester instructions should list the known issues until 0.4.4 lands: avoid rotating before the terminal opens, and do not share project ZIPs after signing in to a CLI.

STAGE 1 (code freeze for 0.4.4: F, E and C only)
4. Bump versionCode to 20 and versionName to 0.4.4. Keep targetSdk 36 and minSdk 26.
5. Run scripts/compile-check.sh and scripts/test-core.sh (with VY_JSON_JAR). Add the new E and C host tests. Save artifacts/vy-build-workflow-host-validation.json and commit and push it (G0 remote).
6. Build the dev APK with scripts/build-on-android.sh. Run the 16 KB alignment verifier on all native libraries. Confirm the manifest declares targetSdkVersion 36. Install it over the dev 0.4.3 and run the phone QA matrix: every Block row must pass.

STAGE 2 (signed bundle)
7. Build the signed AAB with the upload key (scripts/build-review-bundle.sh). Validate it with bundletool. Record its sha256 and whether libvynode.so is inside, which answers NODE-IN-RELEASE. Build a native-debug-symbols.zip of the unstripped .so files per ABI. Without R8/ProGuard, no deobfuscation mapping is needed; confirm that.
8. Turn on Managed publishing so nothing goes live before Melody presses Publish.

STAGE 3 (Play upload)
9. Upload code 20 to the Internal testing track first. Internal testers get the paid app free, and a pre-launch report is generated there too. Upload the native debug symbols. Install the Play-signed build on a second device or a clean install (QA row 2) and run rows 3, 4 and 18 to 20.
10. Read the pre-launch report (QA row 21). Any crash or ANR blocks the release.
11. Promote code 20 to Closed testing 'Alpha' as a new release, with release notes listing F, E and C. If release 19 is still in review, either let that review finish or withdraw it under Publishing overview; I could not confirm how Play handles a second submission during review, so check in Console. Then send for review and publish once approved.
12. On the Play-installed build, run Report response against the live worker (blocker REPORT) and record the result in the bridge plan note.

STAGE 4 (14-day closed test, about 2026-10-23 to 2026-11-06 at the earliest)
13. Check the opted-in count daily; it must stay at 12 or more for 14 continuous days. Log tester feedback and what was fixed, because the production-access application asks about this.
14. Ship 0.4.5 (code 21) with the Agents-tab context work (ledger, stable prefix, shared snapshot, rolling summary) through the same steps, internal then closed. The clock keeps running.

STAGE 5 (production gate)
15. Clear the LISTING blocker:
   - Store copy and screenshots match shipped features (Node, CLIs, no pip or React claims until they ship) and contain no test projects.
   - Data safety re-walked for AI-provider transfers, Report response, crash data and MCP/bridge traffic.
   - Content-rating questionnaire re-checked (unrestricted internet, AI chat).
   - Foreground-service declarations (mediaProjection, specialUse) still accurate.

17. After approval: create a production release with code 20 or 21 and a staged rollout (for example 10%, then 50%, then 100%), watching Android vitals at each step. Production covers 177 countries at US$0.99.

PLAY REQUIREMENTS CHECKED (as of 2026-10-22)
- Target API: since 2026-08-31, new apps and updates must target Android 16 (API 36), with an extension available to 2026-11-01. VY targeted 36 at code 3; re-check it for code 20.
- 16 KB page size: required for apps targeting API 35 or later that contain native code. Sources disagree on the enforcement date: developer.android.com's page-sizes guide says updates are blocked from 2027-02-01, while third-party posts say 2025-11-01 or 2026-05-01. VY already aligns its libraries, so re-verify every build anyway.

- Pre-launch report: generated automatically on the internal, closed and open tracks; it is built on Firebase Test Lab Robo.
- AI-Generated Content policy: requires in-app reporting of offensive AI output.
- Device and Network Abuse policy: no downloading of executable code from outside Play (dex, JAR, .so). Interpreted code is exempt but must not enable policy violations. This affects pip and npm with native packages.
